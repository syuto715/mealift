## Dim A: セキュリティ

### A-01 [Critical] GEMINI_API_KEY can leak to end users via unscrubbed fetch-error messages (key is in the request URL)

- **flags**: 自律  ·  finder: `A1-ef-security`  ·  verify: confirmed
- **files**: `supabase/functions/coach-chat/index.ts`, `supabase/functions/coach-advice/index.ts`, `supabase/functions/coach-routine/index.ts`, `supabase/functions/estimate-nutrition/index.ts`, `supabase/functions/estimate-nutrition-vision/index.ts`, `supabase/functions/nutrition-advice/index.ts`, `supabase/functions/generate-workout-menu/index.ts`, `supabase/functions/generate-weekly-report/index.ts`, `supabase/migrations/20260421000000_create_ai_usage_logs.sql`
- **根拠**: All 8 Gemini EFs put the secret in the URL query string, e.g. coach-chat/index.ts:653 `fetch(\`${GEMINI_URL}?key=${GEMINI_API_KEY}&alt=sse\`, ...)`. Deno network-layer fetch failures throw `TypeError: error sending request for url (https://generativelanguage.googleapis.com/...?key=AIza...): ...` — the message embeds the full URL including the key. That raw message is then surfaced: (a) directly to the client — coach-chat/index.ts:829-834 streams `message: e instanceof Error ? e.message : 'unknown error'` in the NDJSON error event (only AbortError is filtered at :804-811); coach-advice/index.ts:438-446 returns `details: { cause: e instanceof Error ? e.message : String(e) }`; coach-routine/index.ts:464-477 same. (b) to a user-readable table — estimate-nutrition/index.ts:281, estimate-nutrition-vision/index.ts:339, nutrition-advice/index.ts:250, generate-workout-menu/index.ts:538 and generate-weekly-report/index.ts:658+754 all set `errorMessage = e.message` which the finally block inserts into `ai_usage_logs.error_message`, and migration 20260421000000 lines 26-28 grants `select using (auth.uid() = user_id)`, so the owning user can read it via PostgREST. The existing `scrubSecrets` (whose `google_api_key` pattern `AIza[0-9A-Za-z_-]{35}` would catch exactly this) is applied only to LLM output text, never to these error strings.
- **影響**: Any transient Gemini network failure (DNS/TLS/connection reset — routine during upstream outages) hands the platform's Gemini API key to whichever authenticated user's request hit the error, either in the HTTP response body or in a table they can read. A leaked key lets an attacker burn Mealift's Gemini quota/billing directly (money impact) and is not rotatable without a deploy.
- **修正方針**: Two-part, behavior-preserving: (1) move the key out of the URL — send it as the `x-goog-api-key` request header (officially supported by the Generative Language API) so no error message can ever embed it; (2) defense-in-depth, pass every `e.message` destined for a client response or for ai_usage_logs.error_message through the existing `scrubSecrets()` (or replace the client-facing `cause`/`message` with a generic string and keep the detailed message only in console.warn, which is already the pattern used for redaction telemetry).

### A-02 [Important] Unbounded / under-validated client input is interpolated into Gemini prompts (cost exhaustion + injection surface)

- **flags**: 提案  ·  finder: `A1-ef-security`  ·  verify: confirmed
- **files**: `supabase/functions/coach-chat/index.ts`, `supabase/functions/coach-routine/index.ts`, `supabase/functions/generate-workout-menu/index.ts`
- **根拠**: coach-chat/index.ts:303-336 validates ONLY the latest user message: `const lastMessage = (messages as ...).slice().reverse().find((m) => m?.role === 'user')` then `checkUserContentLength(lastUserContent)` (4000-char cap). The full `messages` array — uncapped in element count and per-message content length, including client-forgeable `role:'assistant'` turns — is forwarded verbatim to Gemini at :618-625 (`contents = messages.map((m) => ({ role: m.role === 'assistant' ? 'model' : 'user', parts: [{ text: m.content }] }))`; non-string `content` is also passed through unchecked here since only `lastUser.content` was type-checked). coach-routine/index.ts:130-137 caps exerciseSlugs at 200 elements but each element only needs `typeof s === 'string' && s.length > 0` — no per-item length cap — and they are joined into the prompt at :439-441. generate-workout-menu/index.ts:110-137 has the same gap for both `targetMuscles` (10 items, free text, no length cap, prompt at :162) and `exerciseSlugs` (200 items, no length cap, prompt at :197). By contrast intentText is capped at 400 (coach-routine:76,124-128).
- **影響**: A single authenticated request (even free tier, within quota) can carry megabytes of text into the Gemini call — input tokens are billed even with maxOutputTokens capped — multiplying per-request cost far beyond what the monthly quota model assumes. The uncapped fields are also an unmonitored prompt-injection channel: jailbreak detection (detectJailbreakHints) runs only on the last user message / intentText, so injected instructions in fabricated assistant turns or oversized slug strings bypass the L4 telemetry entirely.
- **修正方針**: Server-side caps mirroring realistic client behavior: coach-chat — cap messages.length (e.g. 50), enforce a per-message content-length cap and total-payload cap, and require content to be a string for every element (reject otherwise); coach-routine / generate-workout-menu — per-item length caps (e.g. slug ≤ 80 chars matching routineJson.ts SLUG_MAX, muscle key ≤ 40 matching projectContext.ts MUSCLE_KEY_MAX_LEN). These tighten the EF request contract, so ship with a client-side check in the same release.

### A-03 [Important] Trial users: server plan gates ignore trial_started_at on 4 of 5 plan-gated AI EFs, contradicting client hasFeature (trial→plus)

- **flags**: 🛑不可侵 / 提案  ·  finder: `A1-ef-security`  ·  verify: confirmed
- **files**: `supabase/functions/coach-advice/index.ts`, `supabase/functions/coach-routine/index.ts`, `supabase/functions/coach-chat/index.ts`, `supabase/functions/generate-workout-menu/index.ts`, `supabase/functions/generate-weekly-report/index.ts`, `src/infra/services/subscriptionService.ts`
- **根拠**: Client: subscriptionService.ts:371-373 `if (status === 'trial') return 'plus'` — during the 7-day trial the UI enables aiCoachGeneration, aiCoachAdviceWeekly, 200-msg chat, 30/mo workout gen (PLUS flag block at :231-236, :223). Server: only generate-weekly-report implements trial detection (index.ts:129-153 `deriveEffectivePlan` — comment explicitly calls the missing-trial handling 'Codex review pass 1 / Critical #1'). The sibling EFs read the raw plan column only: coach-advice/index.ts:277-310 (`select('plan, timezone')`, weekly limit for 'free' is 0 → 403 plan_required), coach-routine/index.ts:244-272 (free limit 0 → 403), coach-chat/index.ts:238-260 (trial user gets free quota 5 instead of 200), generate-workout-menu/index.ts:325-339 (trial user gets 3/mo instead of 30). start-trial only sets trial_started_at; plan stays 'free' during trial (start-trial/index.ts:66-71), so these gates see 'free'.
- **影響**: A trial user is shown the ミー先生 weekly-advice and routine-generation features as unlocked, then gets a hard 403 plan_required from the server — a broken conversion-critical flow during the exact window that decides whether they subscribe. Chat and workout-menu silently degrade to free quotas (5 msgs / 3 gens), undercutting the advertised trial value.
- **修正方針**: Extract generate-weekly-report's deriveEffectivePlan (plan_expires_at > now → paid; else active trial_started_at within 7 days → 'plus'; else 'free') into _shared/subscription.ts and use it in the plan gates of coach-advice, coach-routine, coach-chat and generate-workout-menu (selecting trial_started_at + plan_expires_at alongside plan). Alternatively, if trial is intentionally weekly-report-only, gate the client features off during trial — but current client code says otherwise. Entitlement area — needs product sign-off, do not auto-fix.

### A-04 [Important] generate-weekly-report deriveEffectivePlan treats a paid plan with null plan_expires_at as free, contradicting the C-1 subscription contract

- **flags**: 🛑不可侵 / 提案  ·  finder: `A1-ef-security`  ·  verify: confirmed
- **files**: `supabase/functions/generate-weekly-report/index.ts`, `supabase/functions/_shared/subscription.ts`
- **根拠**: generate-weekly-report/index.ts:136-141: the paid branch requires a future expiry — `if (profile.plan_expires_at && Date.parse(profile.plan_expires_at) > now.getTime()) { return profile.plan === 'pro' ? 'pro' : 'plus'; }` — otherwise it falls through to the trial check and then `return 'free'` (:152). But _shared/subscription.ts explicitly defines null expiry as a valid ACTIVE state: :88-89 `plan_expires_at: active && expMs !== null ? ... : null` with the comment '(a lifetime / non-renewing entitlement may have null expiration)', and planFromSubscriber :111-112 `const active = exp === null || ...` treats null expires_date as active, writing plan='plus'/'pro' with plan_expires_at=null via sync-subscription (sync-subscription/index.ts:99-114). subscription.ts:12-14 also states the RAW plan column 'MUST already reflect *effective* access', so re-deriving from expiry here is a second, disagreeing source of truth.
- **影響**: A paying user whose entitlement has no expiration (lifetime/promotional/non-renewing, or any RC state where expires_date is null) has plan='plus'|'pro' on the server yet gets 402 plus_required from the weekly-report EF — a paying user denied a paid feature. It also means two server modules now disagree about what 'active' means, which will silently diverge further as C-1 evolves.
- **修正方針**: In deriveEffectivePlan, trust the effective plan column first (plan !== 'free' → return it, per the _shared/subscription.ts contract that expired plans are already downgraded to 'free' by the webhook/reconcile), keeping the trial_started_at branch for trial users only. Entitlement/C-1-adjacent — route through the proposal list.

### A-05 [Important] send-push-notifications cron auth fails open when CRON_SECRET is unset (sibling EFs guard this)

- **flags**: 自律  ·  finder: `A1-ef-security`  ·  verify: confirmed
- **files**: `supabase/functions/send-push-notifications/index.ts`, `supabase/functions/cleanup-idempotency-keys/index.ts`, `supabase/functions/revenuecat-webhook/index.ts`, `supabase/functions/_shared/timingSafe.ts`, `supabase/config.toml`
- **根拠**: send-push-notifications/index.ts:192-196: `const provided = auth.startsWith('Bearer ') ? auth.slice(7) : ''; if (!constantTimeEqual(provided, CRON_SECRET)) { ... 401 }` — no empty-value guard. CRON_SECRET is `Deno.env.get('CRON_SECRET')!` (:37); if the env var is missing this is undefined at runtime, and in constantTimeEqual (timingSafe.ts:10-13) `enc.encode(undefined)` yields the empty byte array (TextEncoder's WebIDL default ''), so a request with NO Authorization header (provided='') compares equal → auth passes. The sibling EFs are fail-closed: cleanup-idempotency-keys/index.ts:65 `if (!provided || !constantTimeEqual(provided, CRON_SECRET))` and revenuecat-webhook/index.ts:57 `if (!WEBHOOK_AUTH || !constantTimeEqual(provided, WEBHOOK_AUTH))`. config.toml pins `verify_jwt = false` for this function, so the gateway provides no fallback auth.
- **影響**: Under an env misconfiguration (secret rotation slip, new environment, config drift — the header comment at :31-33 itself flags rotation as a two-place manual step), the endpoint becomes fully unauthenticated: anyone can trigger the service-role outbox drain, force-send queued pushes, burn attempt_count on rows, and cause push_tokens deletions via forged retry timing. Currently benign payloads, but it is an open service-role code path.
- **修正方針**: Match the sibling pattern: `if (!CRON_SECRET || !provided || !constantTimeEqual(provided, CRON_SECRET)) return 401`. One-line, behavior-preserving for the legitimate cron caller.

### A-06 [Important] Supabase auth session (access + refresh tokens) and user email persisted in plaintext AsyncStorage instead of SecureStore/encrypted storage

- **flags**: 提案  ·  finder: `A2-client-security`  ·  verify: confirmed
- **files**: `src/infra/supabase/client.ts:34-43`, `src/stores/authStore.ts:290-297`
- **根拠**: src/infra/supabase/client.ts:34-43 configures the Supabase client with unencrypted AsyncStorage as the session store: `createClient(supabaseUrl, supabaseAnonKey, { auth: { storage: AsyncStorage, lock: processLock, persistSession: true, ... } })`. The session blob written there contains the access JWT and the long-lived refresh token in plaintext (AsyncStorage on Android is an unencrypted SQLite file in app data; on iOS an unencrypted file in the app container, unlike Keychain). Additionally src/stores/authStore.ts:290-297 persists `user` (id + email) to the same plaintext store: `storage: createJSONStorage(() => AsyncStorage), partialize: (state) => ({ isAuthenticated, isLocalOnly, user: state.user })`. The gap is acknowledged in-code (client.ts:24: "Build 16+ TODO 11 still tracks a possible MMKV migration; for now uniformity with everything else in the project wins") but the tracked migration is to plain MMKV, which is also unencrypted by default — the security-relevant target is expo-secure-store (Keychain/Keystore) or MMKV with an encryption key held in SecureStore.
- **影響**: The refresh token grants indefinite account access (chat history, meals, body weight, progress-photo metadata, subscription state via authenticated EF calls). Plaintext at-rest storage exposes it to device backups (Android autoBackup/adb backup depending on manifest config), rooted/jailbroken devices, and any future arbitrary-file-read vulnerability in the app or OS. Same class for the persisted email (PII). This is a hardening gap rather than a remotely exploitable hole, but it covers the app's single most sensitive client-side credential.
- **修正方針**: Provide a SecureStore-backed storage adapter for the Supabase auth client (expo-secure-store implements the same getItem/setItem/removeItem contract; values >2KB need chunking or the common pattern of an AES key in SecureStore encrypting an MMKV/AsyncStorage payload). Migrate lazily on boot: read existing session from AsyncStorage, write to the secure adapter, delete the old key. Keep the zustand auth mirror storing only non-sensitive flags (drop `user.email` from partialize or move it to the secure store too). Must be done carefully — session-persistence races (processLock, probeSession Tier 2 recovery, authBootstrap) all assume this storage layer, so this needs its own verified sprint, not an in-place swap.

### A-07 [Important] Unused RECORD_AUDIO permission and untranslated English microphone/photo-add purpose strings ship in production builds

- **flags**: 提案  ·  finder: `A3-config-scripts`  ·  verify: confirmed
- **files**: `app.config.ts`, `ios/app/Info.plist`
- **根拠**: app.config.ts:75-83 explicitly requests audio recording: permissions: [... 'android.permission.RECORD_AUDIO', 'android.permission.READ_EXTERNAL_STORAGE', 'android.permission.WRITE_EXTERNAL_STORAGE', ...]. Repo-wide search confirms zero audio capture usage: no expo-av/expo-audio imports, no CameraView mode="video", no recordAsync anywhere in src/ or app/ (expo-camera is used only for still photo + barcode in app/scan-label.tsx, app/scan-dish.tsx, app/barcode.tsx). Because expo-camera's config plugin is auto-applied at prebuild without a plugins entry, the generated iOS Info.plist also contains the default English boilerplate — ios/app/Info.plist: <key>NSMicrophoneUsageDescription</key><string>Allow $(PRODUCT_NAME) to access your microphone</string> and <key>NSPhotoLibraryAddUsageDescription</key><string>Allow $(PRODUCT_NAME) to save photos</string> — while every other purpose string is properly localized Japanese. READ/WRITE_EXTERNAL_STORAGE are additionally legacy no-ops (the generated manifest also carries android:requestLegacyExternalStorage="true").
- **影響**: Privacy over-permission: the app declares microphone access it never uses. On iOS the permission dialog (if ever triggered) and App Privacy review show an untranslated 'Allow $(PRODUCT_NAME) to access your microphone' template string to Japanese users — Apple has rejected apps under Guideline 5.1.1 for boilerplate purpose strings. On Android, Google Play's sensitive-permission review flags RECORD_AUDIO with no in-app use, and WRITE_EXTERNAL_STORAGE is rejected outright for targetSdk 30+ without a declaration; this becomes a launch blocker when the Android release (currently versionCode 1, unshipped) goes to Play.
- **修正方針**: In app.config.ts: (1) remove 'android.permission.RECORD_AUDIO', 'android.permission.READ_EXTERNAL_STORAGE', 'android.permission.WRITE_EXTERNAL_STORAGE' from android.permissions; (2) add an explicit ['expo-camera', { cameraPermission: '進捗写真を撮影するためにカメラへのアクセスが必要です。', microphonePermission: false, recordAudioAndroid: false }] plugin entry so the auto-applied plugin stops injecting the mic permission/string; (3) give expo-media-library (source of NSPhotoLibraryAddUsageDescription) a Japanese savePhotosPermission string via its plugin config. Requires a new native build to take effect — schedule with the next build, verify permissions diff via npx expo prebuild --clean on a branch before submitting.

### A-09 [Nit] Quota gates are count-then-insert (TOCTOU) across all AI EFs — known, documented, still open

- **flags**: 提案  ·  finder: `A1-ef-security`  ·  verify: nit-unverified
- **files**: `supabase/functions/estimate-nutrition-vision/index.ts`, `supabase/functions/estimate-nutrition/index.ts`, `supabase/functions/nutrition-advice/index.ts`, `supabase/functions/coach-chat/index.ts`, `supabase/functions/coach-advice/index.ts`, `supabase/functions/coach-routine/index.ts`, `supabase/functions/generate-workout-menu/index.ts`, `supabase/functions/generate-weekly-report/index.ts`
- **根拠**: estimate-nutrition-vision/index.ts:183-197 documents it in-code: 'Known TOCTOU: this count-then-insert pattern ... two parallel calls from the same user can both observe count < limit, both proceed ... TODO(v1.5 quota race): replace count-then-insert with an atomic RPC'. The same SELECT count → later INSERT ai_usage_logs pattern exists in every quota-gated EF (e.g. coach-chat/index.ts:260-286 count, :518-526 insert; generate-workout-menu/index.ts:345-378 count, :549 insert).
- **影響**: A user scripting parallel requests can overshoot their daily/monthly AI quota by roughly the concurrency width (e.g. a free user firing 20 parallel coach-chat requests lands ~20 instead of 5). Bounded cost abuse, not a correctness break; already acknowledged as a deferred TODO.
- **修正方針**: As the in-code TODO says: an atomic RPC (gate + usage-log insert in one statement/transaction, e.g. `insert ... select ... where (select count(*) ...) < limit returning id`) shared by all AI EFs. Requires a Supabase migration for the RPC, hence proposal-only.

### B-01 [Critical] Server natural-key unique indexes vs id-keyed upsert: cross-device same-date rows permanently dead-letter on push AND wedge pull on body_logs

- **flags**: 提案  ·  finder: `B1-sync-integrity`  ·  verify: confirmed
- **files**: `src/infra/supabase/sync/syncHelpers.ts:61-84`, `src/infra/supabase/sync/bodyLogSync.ts:96-103`, `src/infra/supabase/sync/bodyLogSync.ts:58-73`, `supabase/migrations/20260505000000_create_user_sync_tables.sql:158-160`, `supabase/migrations/20260505000000_create_user_sync_tables.sql:390-392`, `supabase/migrations/20260505000000_create_user_sync_tables.sql:428`, `src/infra/database/migrations/v1.ts:41`, `src/infra/repositories/syncRepository.ts:141-164`
- **根拠**: Push always upserts by id: syncHelpers.ts:65 `onConflict: string = 'id'` and bodyLogSync.ts:102 `await upsertWithBackoff(client, SERVER_TABLE, payload)` (no key override). But the server enforces natural keys: 20260505000000.sql:158 `create unique index ... user_body_logs_user_date_unique on public.user_body_logs (user_id, date) where deleted_at is null;` and :390 `user_meal_logs_user_date_meal_unique ... (user_id, date, meal_type)`. Two devices (or a reinstall-then-login) that each create a body_log / meal_log for the same date generate different ids; the second push is an INSERT that hits 23505, which isRateLimited() treats as terminal -> throw -> markFailed -> after MAX_RETRIES=5 the row is dead-lettered (syncRepository.ts:154-156) with no recovery UI. For meal_logs, all child user_meal_log_items then fail the NOT NULL FK (:428 `meal_log_id uuid not null references public.user_meal_logs(id)`) and dead-letter too — the whole day's meals from that device never reach the cloud. Pull direction is worse for body_logs: local schema v1.ts:41 has `UNIQUE(profile_id, date)`, and applyServerRow (bodyLogSync.ts:58-73) is `INSERT ... ON CONFLICT(id) DO UPDATE` — pulling the other device's same-date row (different id) violates the local (profile_id,date) unique, runAsync throws, pullAll catches and breaks (syncOrchestrator.ts:260-265), and the watermark never advances past that row: body_logs pull is permanently wedged on that device, silently, every run.
- **影響**: Any user who logs weight or meals for the same date on two devices (or reinstalls and logs before signing back in) silently loses that data from cloud sync (dead-letter, no UI), and on body_logs additionally loses ALL future pulls of the resource on the second device. - **修正方針**: Design-level: for tables with server natural keys, push with onConflict on the natural key (user_id,date / user_id,date,meal_type / user_id,week_start), mirroring the userEquipmentSync composite-key pattern (userEquipmentSync.ts:132-137), and make the local pull-apply upsert also handle the natural-key conflict (ON CONFLICT(profile_id,date) merge with the updated_at guard, keeping the server id). Additionally, treat 23505 as a merge signal rather than a terminal error. Requires careful id-reconciliation like the user_equipment module; not safe to auto-fix.

### B-03 [Important] Tombstone pull hard-DELETE vs local RESTRICT FKs: deleting a used custom exercise permanently wedges the exercises pull stream (incl. the originating device)

- **flags**: 🛑不可侵 / 提案  ·  finder: `B1-sync-integrity`  ·  verify: confirmed
- **files**: `src/infra/supabase/sync/syncHelpers.ts:106-118`, `src/infra/supabase/sync/customExerciseSync.ts:137-139`, `src/infra/database/migrations/v1.ts:76-77`, `src/infra/database/migrations/v1.ts:106-107`, `src/infra/database/connection.ts:74`, `src/infra/repositories/workoutRepository.ts:557`, `src/infra/supabase/sync/syncOrchestrator.ts:250-265`

AND is_custom = 1`), which works locally because the row is kept — but when the pushed tombstone comes back through pull, customExerciseSync.ts:139 calls applyServerDeletion on `exercises`; if any workout_set or routine_item references it (normal after using the exercise), the DELETE throws SQLITE_CONSTRAINT. pullAll (syncOrchestrator.ts:260-265) catches, breaks, and never advances the watermark — so the same tombstone is retried and fails on EVERY subsequent sync, permanently blocking all newer custom-exercise rows from pulling, on every device including the one that deleted it. ### B-04 [Important] Push retry budget can be burned in a single sync run: >=50 failing rows of one table are dead-lettered in one tight loop with no cross-run backoff

- **flags**: 提案  ·  finder: `B1-sync-integrity`  ·  verify: confirmed
- **files**: `src/infra/supabase/sync/syncOrchestrator.ts:196-222`, `src/infra/repositories/syncRepository.ts:97-109`, `src/infra/repositories/syncRepository.ts:141-164`
- **根拠**: pushAllPending drains per table: after a batch, `if (batch.length < PUSH_BATCH_LIMIT) break; batch = await getPendingForTable(...)` (syncOrchestrator.ts:216-220). getPendingForTable returns rows `WHERE synced_at IS NULL AND retry_count < ?` (MAX_RETRIES=5) ordered by created_at (syncRepository.ts:103-107). If a full batch of 50 rows all fail (network drop mid-run, server 5xx, RLS/schema error), markFailed only bumps retry_count, so the refetch returns the SAME 50 rows, which fail again immediately — the loop repeats 5 times back-to-back and moveToDeadLetterInternal (syncRepository.ts:154-156, 182-203) permanently retires the entire backlog within seconds of one run. The intended '5 retries across runs' semantics only hold when fewer than PUSH_BATCH_LIMIT rows are pending. Dead-lettered rows require manual recovery that has no UI ('Future Phase 9', syncRepository.ts:120-124).
- **影響**: A user who accumulated 50+ offline changes in one table (a day of meal_log_items easily exceeds this) and hits a transient outage during their next sync loses the whole backlog from cloud sync permanently and silently.
- **修正方針**: Stop the per-table drain loop as soon as an iteration made no forward progress (uploaded === 0 for the batch), so each run consumes at most one retry per row; optionally add retry_count-based exponential scheduling (next_attempt_at column would need a migration, so the minimal fix is the no-progress break).

### B-05 [Important] Watermark pagination uses strict gt + last-row timestamp: batches of rows sharing one updated_at are permanently skipped past the batch limit

- **flags**: 提案  ·  finder: `B1-sync-integrity`  ·  verify: confirmed
- **files**: `src/infra/supabase/sync/syncHelpers.ts:126-147`, `src/infra/supabase/sync/bodyLogSync.ts:127-130`, `src/infra/supabase/submissionSync.ts:244-252`, `src/infra/supabase/submissionSync.ts:305-308`, `src/infra/supabase/sync/syncOrchestrator.ts:244-259`
- **根拠**: fetchWatermarkBatch: `.gt('updated_at', watermark).order('updated_at', { ascending: true }).limit(limit)` (syncHelpers.ts:134-140) with no id tiebreaker, and every module returns `newWatermark: rows[rows.length - 1].updated_at` (e.g. bodyLogSync.ts:129). Server updated_at is set by the set_updated_at() trigger to now(), which is TRANSACTION-stable in Postgres — any single-transaction bulk update (moderator batch-approval of public_foods, server-side maintenance/backfill UPDATE across a user's rows) stamps an identical updated_at on every touched row. If more than PULL_BATCH_LIMIT(500) rows share that timestamp, the first 500 are pulled, the watermark is set to that exact timestamp, and the next query's strict `.gt` excludes ALL remaining identical-timestamp rows forever. The same off-by-tie exists at every batch boundary (row 501 sharing row 500's timestamp is skipped). submissionSync.pullApprovedSubmissions (:250-252,:307) has the identical pattern for approved_public_foods, where bulk approvals in one transaction are the realistic operational mode.
- **影響**: Silent, permanent non-delivery of rows: a device doing initial/backlog pull can lose an unbounded slice of server data with no error and no retry, because the watermark records the skipped rows as 'done'.
- **修正方針**: Keyset pagination on (updated_at, id): order by updated_at,id and use `or(updated_at.gt.W, and(updated_at.eq.W, id.gt.lastId))`, or simpler: use gte with id-dedup and only advance the watermark when the last batch was not full. Touches every pull module's contract, so proposal-only.

### B-06 [Important] Conflict resolution compares server ARRIVAL time, not event time: a late-pushed tombstone deletes newer edits despite the edit-wins guard

- **flags**: 🛑不可侵 / 提案  ·  finder: `B1-sync-integrity`  ·  verify: confirmed
- **files**: `src/infra/supabase/sync/syncHelpers.ts:99-118`, `src/infra/supabase/sync/bodyLogSync.ts:99-101`, `supabase/migrations/20260505000000_create_user_sync_tables.sql:45-51`
- **根拠**: Server updated_at is trigger-maintained: `new.updated_at = now()` on every update (20260505000000.sql:48-51); push payloads never include updated_at, and pushOne stamps DELETE tombstones with push time, not deletion time: `payload.deleted_at = new Date().toISOString()` (bodyLogSync.ts:100). applyServerDeletion's edit-wins guard (syncHelpers.ts:112-117) compares `local.updated_at <= tombstone.updated_at`, where tombstone.updated_at is the server upsert (arrival) time. Sequence: device A deletes a row at T1 while offline; device B edits the same row at T2 > T1; A comes online at T4 and pushes the tombstone — server updated_at becomes T4 > T2, B pulls the tombstone, guard passes (T2 <= T4), and B's strictly newer edit is hard-deleted. The documented intent ('local row edited AFTER the server deletion ... the edit wins', syncHelpers.ts:101-104) only holds relative to sync timing, not to what the user actually did; in an offline-first app late pushes are the norm, so the older action routinely wins.
- **影響**: Multi-device delete-vs-edit races resolve by push order rather than user action order — health data (weights, meals, workouts) edited on one device can be silently removed by a stale deletion synced later.
- **修正方針**: Carry a client edit/delete event timestamp (e.g. client_updated_at, or reuse the payload's local updated_at / deleted_at instead of new Date() at push time) and compare tombstones against that, keeping the server trigger only for pull-watermark ordering. Requires a server column + contract change; also this is the sealed tombstone edit-wins layer.
